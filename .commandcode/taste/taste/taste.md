# Taste
- Wants full understanding and clarification before implementation: read and evaluate the source material first, ask blocking questions, and wait for answers rather than starting to build. When they ask for an explanation ("drop answer below", "just explain", "let me know only"), answer in the chat and change no files. Confidence: 0.75
- Do not modify source/data files during review or analysis work — report findings and recommendations in the chat/README only, leaving files untouched ("Do not change any file, only write here"). Confidence: 0.8
- Wants one canonical naming convention for items across the whole system — no variant spellings/aliases per sheet; align every sheet to the canonical names used in the master Stock list. Confidence: 0.75
- Wants explanations and questions phrased in plain, easy language with no jargon, because they need to understand what they're answering ("Ask in easy language so i can understand easily"). Confidence: 0.75
- Explains their own rules in their own words when asked, so offer an "I'll explain in my words" escape hatch instead of only fixed-option questions. Confidence: 0.5
- Edit existing documents incrementally — keep the current structure and wording, add sections/details rather than rewriting, and never delete important details; strip only what is now unnecessary. Confidence: 0.75
- Expects spec/README documents to be self-sufficient references that capture the full understanding plus the known gaps, not brief summaries. Confidence: 0.6
- Wants decisions agreed in chat written back into the spec/README before implementation starts ("Update the readme first the decisions we have just made. Then tell me if you are ready") — docs-first workflow, not code-first. Confidence: 0.65
- After a change is delivered, wants a plain-language explanation of the surrounding operational steps: which actions they will still need to run and exactly when to run them (e.g. "tell me why i need Setup/Update Structure script and when"), so they can operate the tool themselves without guessing. Confidence: 0.55
- Wants every rate/cost the system uses to be visible as its own column in the report and derived from the actual source records (what was really paid on the purchase row, weighted as an average), never a default or "latest" value applied silently — so they can see which number is being multiplied and where it came from. Confidence: 0.6
- Prefers one general formula/rule for calculations over chained special-case branching — e.g. a single rate/unit conversion rule that covers every case so no value is dropped ("Drop best formula for rates units so no value drops"). Confidence: 0.6
- Prefers large builds delivered phase by phase with review checkpoints, so they can track progress and correct it early, rather than one big drop at the end ("go phase by phase? So i can track and help you make it better"). Confidence: 0.6
- Wants data-entry forms to be minimal and complete on one screen: the date plus every input field visible at once with a single Save, not fields that appear via script/conditional state; and editing an existing record should show its loaded values plus a visible Delete button. Confidence: 0.55
- Wants edit and delete available from the sidebar UI for every kind of record so they never have to touch the sheet rows by hand ("so i dont have to touch the table row manually"), and wants each new area to reuse the interaction pattern already built elsewhere ("I want to do the same for Bazar too"). This extends to filtering: a new tab's filters should mirror the pattern already working in another tab within its date range ("just like we can filter batches by preparations under date ranges"). Confidence: 0.65
- Prefers list views on data-entry screens to be scoped to the selected date, not auto-loading the last N records ("instead of loading last 100 bazar i think date filteration is much better... a new date when there is no bazar added yet, the list will be empty"). The date field should drive both browsing and adding (adding a record uses the clicked date), clicking a row loads its data into the form in edit mode with update/delete available, and the backing sheet should be kept sorted by date so backdated entries land in the right place. Confidence: 0.7
- Wants typed values preserved verbatim in saved tables: a typed `0` must be stored and displayed as `0` (not collapsed to blank), and a field left empty on save should default to `0`, so every saved row shows actual numbers. Confidence: 0.55
- Wants reporting exposed as a UI, not just internal functions: summary views reachable from the menu (e.g. Awwffle → Summary → Batches) that let them filter by all-time, specific dates and date ranges to get totals, rather than verifying numbers from test output. Confidence: 0.6
- Prefers to accept the assistant's proposed plan as-is and start implementing it, then evaluate the working result and tweak afterward, rather than refining the plan up front ("start with your plan and see how that works out, then will evaluate and tweak if needed"). Confidence: 0.5
- Expects every report figure to earn its place: drop grand totals and combined averages that answer no real question ("No need for 'Batches made' which is total… since batches are all different"), and show a per-category breakdown — each category's own total and its own average — plus a filter to narrow the report to a single category. Keep only the counts that are genuinely useful (records, open/calendar/closed days), and make each metric context-aware — e.g. show per-item rate stats only when a single item is selected, since combinations like "avg per open day" or an average rate across mixed items mean nothing ("Make it realistic... rather show whats useful"). Confidence: 0.75
- After something is built, wants each column/metric explained in plain terms, checked against their real business data (e.g. "every time I make it I make 2 batches — is it aligned?"), and a candid verdict on whether it actually helps them, including where it can mislead — not just a report that it is done. Confidence: 0.6
- Optimises for the long term, not just the current data: solutions should be built "best for future and easy to maintain" — general, configurable and changeable later (e.g. off-days as editable dated records that may move to two days, a different day, or none) rather than hardcoded to today's pattern. Confidence: 0.6
- Sketches requirements as a rough idea and hands the design over ("Just giving you an idea… you do it better as needed"), but the resulting numbers must be exact and business-realistic ("The calculations should be perfect and realistic"). Take the intent and design the details; never approximate a figure. Confidence: 0.6
- Prefers a compact visual cue over an explanatory sentence: where a figure is above/below par, show a red/green directional arrow on the number itself instead of prose like "Flour is paying more than average". Confidence: 0.55
- Wants quantities shown in the unit they think in, not just a raw dump: for an item bought by the piece but stocked by weight (Nutella, whipped cream) show the piece count alongside the base-unit figure, and when a problem exists (item is low on / below zero stock) surface it as a red callout naming that item instead of a quiet muted "Remaining: 2975 gm" line. Confidence: 0.55
- Dislikes displays that repeat data they can already read in the underlying sheet: hide a detail table (e.g. a per-day list) when the view is unfiltered/all-time, and show it only when a narrower filter makes it add something. Confidence: 0.5
- In filtered report views, categories with no records in the chosen range should be left out entirely rather than shown as rows of zeros ("no need to have their avg cost in the By Preparation table, it will be 0"). Confidence: 0.55
- When asking for an alternative metric or view, wants the existing one kept and switchable back to, not replaced ("We can toggle back… Meaning its better for me to have both"). Confidence: 0.5
- Wants fixes scoped narrowly to the reported defect: repair the one thing that is wrong and leave every other working part untouched ("Keep everything else as is since its perfect") — no opportunistic refactors or rework of behaviour they are happy with. Same when asking for a speed fix ("it's still slow… check again and do not change any data or functionalities, just make it smooth and better optimized"): make it faster, but "keep the functionalities" — speed must never be bought with changed figures or dropped features. Confidence: 0.7
- In the sidebar UI, wants an explicit loading state whenever new filtered data is being fetched: a visible spinner/overlay and all controls in that pane (pills, dates, Show Batches / Show Spending, etc.) disabled until the new numbers arrive, so a second click cannot fire another request and produce a mixed/confusing data set. The previous figures should stay visible behind the overlay rather than blanking and then jumping to new values. This is expected to be uniform across panes: when one filter panel has the pattern, they ask for it in the next one by reference ("add the loading like we had in batches bazar stock while filtering, same needed here in pos filter as well"). Confidence: 0.75
- Wants a fixed colour semantics for figures in the UI: anything "used"/consumed (used cost, total used gm/ml/pieces) is shown in red, anything "remaining" (remaining value, remaining stock) in green, and everything else left in the default black — colour is the status signal, applied consistently everywhere. Money/takings tiles are the exception: the headline amount (e.g. "Total POS Sale") is shown in the green success colour (`#188038`), and they notice when the colour rule is simply missing rather than intended. Confidence: 0.6
- Wants money figures labelled with their currency: any tile showing taka carries a `৳` before the amount ("like for Flour Used Cost ৳2422"), while non-currency figures (counts, days, quantities) stay exactly as they are and tables are left unadorned. Confidence: 0.55
- Deploys by manually pasting files into the Apps Script editor, so hand-off instructions should be terse and concrete — exactly which files to overwrite vs. create, then the exact functions to run and in what order ("Just drop the steps") — not narrative docs. Confidence: 0.55
- Money metrics must be named for what they actually measure and computed with the intended rate: gross takings are "Total POS Sale" (units × sale price), while "POS Revenue" means sale − cost (gross margin) — never labelled "Revenue" when it is just the sale amount. Two tiles showing the same number is a bug, not a convenience, and a figure that comes out implausibly small (e.g. a product showing its cost rate as its sale price) is treated as a wrong-rate defect to trace and repair, not a rounding question. Confidence: 0.6
- Wants date filters to come with ready-made preset ranges (All time, Today, Yesterday, Last 7 days, This month, Last month) as one-click chips alongside the manual From/To pickers, and the selected range spelled out in readable form using weekday names ("Range: Wed Oct 30, 2026 - Fri Nov 17, 2026") because the weekday tells them whether a day was closed — never raw ISO dates like "2026-10-30". Confidence: 0.6
- Prefers risky or legacy actions removed from the menu/UI entirely rather than left in place — they would rather lose the capability than have an accidental click corrupt data ("remove the connection of that import so i dont make any mistake later… we can remove it always so we dont click it and make mistake"). Safety and one-way simplicity over keeping dead paths reachable. Confidence: 0.65
- Prefers low-friction daily aggregate entry (date + amount + optional note, plus a customer picked from a remembered list) over per-invoice/per-transaction detail: linking each figure back to the specific sale, waffle or batch it came from is "too much for me to see and enter" — keep the daily total trustworthy and simple, and let a typed new name/option persist so it appears in the dropdown next time. Confidence: 0.6
- Documentation is part of the deliverable, not a follow-up: when asking for a build, expects the matching markdown docs updated in the same pass ("go build and update md files where needed"), and the new code to stay aligned with the existing documented functionalities and calculations rather than drifting from them. Confidence: 0.55
- Date-range filters should not auto-query on every date change: presets only fill the From/To values, and an explicit "Show …" button (e.g. "Show Discounts") below the date range is what starts the fetch and the loading state — one deliberate action, no hidden `change`-event refreshes. Confidence: 0.55
- Long option lists in the UI should be grouped under labelled categories in a fixed, business-meaningful order (Recipes → Toppings → Equipments; expense types for Bazar) instead of one flat scroll, "so i dont get confused and lost" — usability over compactness, while keeping the existing placement and functionality. Once they approve a pattern like this in one dropdown they expect it applied to the sibling dropdowns too ("in bazar item dropdown too"), not just the one they first mentioned. Confidence: 0.6
